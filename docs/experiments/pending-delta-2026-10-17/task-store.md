# 显式任务增量持久化：存储层结果

本轮证明了单项任务更新、按需读取与 session 归属查询的成本下降；没有证明完整任务读取更快或任务数据库更小。它使用更多的出现编号和索引换取可验证的更新目标与局部访问。完整读取仍保留校验，实测更慢；大型 header 仍整体序列化。

## 对照和隔离

- 基线为 `7cf3918` 的独立只读归档，当前代码在 `codex/exploration-layered-refactor` 工作区。
- 所有数据库由基准或测试在系统临时目录创建、关闭和删除；没有读取或迁移现有任务数据库，没有浏览器、服务操作。
- 当前被测存储源码和基准 SHA-256 逐样本保存；最终文件清单见 `evidence/task-store/files.json`。24 个正式样本的源码摘要一致，每一对基线/新版 fixture 与最终业务内容摘要相同。
- `pilot/` 为初始实现；`full-status-index-pilot/` 为全量状态索引版本。它们保留负面结果，均不混入最终汇总。正式样本把仅剩的 10 个活动项放在保留历史的末尾，要求查询跳过旧记录。

## 契约与边界

schema v3 在有序 `task_items` 增加独立 `occurrence_id`。业务 id 相同、标题相同的两个条目仍有不同持久化编号；编号不参与控件身份、状态等价或覆盖判断。

- `taskState` 完整校验并加载一次任务，返回同步版本和各位置的出现编号。
- `applyTaskDelta` 必须携带该持久化版本，明确声明更新、追加、删除和最终排序。它只序列化指定条目，使用一个 SQLite immediate 事务发布 header、plan、round、计数和新版本。pending dispatch、unknown、预算与相应记录保持原子性；过期版本失败，不能自动回退覆盖。
- 删除/重排必须保持完整的编号排列；重复、缺失、错误编号及不完整排列均回滚。追加的编号由调用者独立生成。重排是结构操作，允许读取和改写相关序号，不声称其成本为常数。
- 原 `save(task, expectedVersion?)` 保持完整深扫描兼容。它不按对象引用跳过嵌套变化。改变的 positional row 没有出现身份连续性证明，因而获得新编号；调用者用 `taskOrder` 刷新句柄，无须再次解码所有历史 JSON。兼容 API 未传版本仍沿用旧的无条件保存契约；运行时编辑路径应显式传版本。
- `taskHeader`、`taskItems` 和 `taskIdForSession` 避免为状态检查、活动页或事件归属解码全部任务。返回条目检查摘要、出现编号和序号范围；session 查询检查选中 round 的摘要，并保留最早创建且满足过滤条件的任务语义。
- 活动索引只包含 `pending/unresolved/blocked` plan。仅当请求状态全部属于该集合时使用；请求混合、其它或未来未知状态时走通用查询，不缩窄请求。每份正式 delta 基准记录了实际 SQL 的 `EXPLAIN QUERY PLAN`，均确认使用 `task_active_items`。
- 局部读取只校验返回条目，不构成完整历史一致性或探索完成证明。历史成功、unknown 和来源证明不能因不在活动页中就丢弃。
- 重启暂停只读取 header 与最后一个 round，并与 decision 失效及事件同事务。unknown 和 A/B 来源保留。

v1/v2 到 v3 的迁移是原子、向前迁移。v2 原有条目 JSON、摘要、顺序和同步版本保留；迁移时完整校验，损坏则整个升级回滚。旧二进制拒绝 v3；回退代码需要相匹配的旧库一致性备份，不能假定新进展自动降级。没有对用户的现有库执行迁移。

## 同输入微基准

每组在独立进程运行 3 次，交替基线/新版顺序；表中为各进程中位数的中位数。每次 80 次单项 plan + 最后 round + header 更新，100 次各类局部读取和 20 次完整读取。SQLite 保持默认 1000 页 WAL 自动 checkpoint，初始 checkpoint、结束关闭合并 WAL；没有 VACUUM。

“大 header” 使用真实 `obligations.entries` 结构，每条 plan 对应一个投影条目；1000 项 header 为 235,214 B，5000 项为 1,191,215 B。小 header 395 B。活动页仅读最后 10 个待测项。

|---|---:|---:|---:|---:|
| 1000 / 小 | 2.336 → 0.111 ms | 2.878 → 0.089 ms | 2.792 → 0.0087 ms | 2.911 → 3.276 ms |
| 1000 / 大 | 2.687 → 0.515 ms | 3.396 → 0.135 ms | 3.374 → 0.577 ms | 3.386 → 3.937 ms |
| 5000 / 小 | 11.809 → 0.110 ms | 14.209 → 0.093 ms | 13.905 → 0.0092 ms | 14.303 → 16.561 ms |
| 5000 / 大 | 13.833 → 2.092 ms | 17.518 → 0.297 ms | 16.774 → 2.841 ms | 16.931 → 19.820 ms |

session 归属查询从 2.86–16.86 ms 降为约 0.015–0.017 ms（这个单任务样本已经避免了解码整份任务；没有宣称其等同于多任务真实事件处理耗时）。完整读取仍慢约 12.5%–17.1%。大型 header 显著限制了增量更新的收益，不能把整个任务模型称为 O(delta)。

出现编号和索引让关闭数据库增加约 15.4%–26.5%，WAL 口径也更大。本轮不是任务存储减量方案。partial index 比全量状态索引减少了静态开销，但未抵消出现编号与唯一索引的成本；两版完整证据均保留。旧证据文件分块节省不能挪用为此任务库的收益。

## 验证与证据

专属 13 项与旧 normalized 10 项共 23/23 通过：包括不触碰未修改条目的 `toJSON` 故障注入、重复业务 id 的独立出现、删除/循环重排、两个连接版本竞争、最后 header 写失败及中间 round 写失败的全事务回滚、unknown 重启保留、损坏返回行拒绝、混合/未知状态查询、session 所有者筛选、v2 精确保留及损坏升级回滚。

- `evidence/task-store/tests.json`、`tests.log`：23 项正式结果。
- `evidence/task-store/summary.json`：4 种规模/头部组合汇总，包含 CPU、磁盘和限制。
- `evidence/task-store/full-*.json`、`delta-*.json`：24 个原始样本，逐样本包含输入/输出/源码/基准摘要；delta 还包含实际 SQL 查询计划。
- `evidence/task-store/commands.json`：完整执行参数和退出码。
- `evidence/task-store/files.json`：本工作线源码文件摘要。
- `typecheck.log` 保留一次并行整合期间的真实失败：另一份新测试 fixture 缺 `goal`。后续总体类型验证由主线程统一执行，不用此文件宣称最终类型检查通过。

运行时真正接入、完整探索协议以及 A 漏测修复属于同轮其它工作线，见主报告；上述局部 API 基准不代替它们，也不证明真实网页穷尽。
