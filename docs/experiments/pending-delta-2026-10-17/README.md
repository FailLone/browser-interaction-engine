# 共享控件漏测修复与实际任务增量读写

本轮并行完成两个工作项：修复共享标识场景中可区分的 A 被漏测，以及让实际探索运行时使用显式增量持久化。前者修复了插件范围投影丢失 SDK 已有语义的问题；后者减少反复序列化历史计划/轮次，并用版本冲突检测保护 unknown、预算和待测记录。没有替换 SDK 覆盖验证、恢复路线或浏览器框架。

结论有边界：受控实验支持这两个改造方向；单项保存和按需读取明显变快，但任务库体积增加，全量读取变慢。不能把之前证据文件分块的压缩收益算成本轮任务库的收益，也不能据此宣称真实 OKX 已穷尽或恢复更快。

## 已落地的调用链

### 1. 保留 SDK 已有的目标语义

`browserOperationKey` 原本包含控件 owner/binding。原插件 `scopeFor` 只投影出 stableKey、名称、角色等字段，导致同名、共享 id 的 A 和 B 范围相同；调度的唯一性检查于是把两者都挡住。A 消失后只剩 B，才执行 B。这不是 SDK 已把两个控件认成同一个，也不是 B 成功被错误记给 A。

适配器抽出已有绑定投影为 `browserControlBindingKey`，插件将其保留为可选 `Scope.targetBinding`；范围匹配、路径推导、列表旧键迁移缓存一并接入。操作条件 key 和 stableKey 的原义保持，旧用户范围仍按原字段匹配。语义也完全相同的重复控件继续拒绝，不引入 DOM 序号强行消歧。摘要只约束任务范围，执行和历史覆盖仍由 SDK 核对。

[详细根因、反例和兼容说明](shared-a.md)。受控共享标识场景同协议 5 次，A/B 都执行由 **0/5 → 5/5**；每轮 A/B 各一次，无重复点击、错误覆盖或模型调用。计划条目由 6 增至 7，是原合并目标被区分；待测条目由 5 降至 3，没有强制清空未测范围。

### 2. 显式增量写入实际运行时

`ExplorerPlugin.start → ExplorerStore.taskState → TaskWriter → applyTaskDelta`。开始执行前仍完整读取并校验任务历史；调度保留历史成功、unknown 和覆盖来源，不能只读取 pending 就丢弃这些证据。

- `TaskWriter` 为每个持久化出现维护独立编号，显式记录改变的 plan 与历史 round；每次同时提交当前 round 和 header。编号不参与控件身份或覆盖等价判断。对象引用仅关联编号，不充当“嵌套内容没变”的证据。
- plan/round 成员数组冻结，追加必须走登记接口，未登记替换/重排会失败。初始化计划与旧数据迁移使用明确的 CAS 全量保存边界，再刷新出现编号。
- 派发前的 `pendingDispatch`、调度选择、尝试记录、相关 plan 与预算同事务提交；unknown 结果提交也保持原子性。旧版本失败后停止旧调度，不能自动退回无条件全量保存，不能重新读取后覆盖新 unknown。
- CAS 保护数据库发布，不回滚已发生的浏览器调用，也不提供多进程浏览器所有权租约；版本冲突后的旧调度停止，不能将这种停止算成浏览器状态还原。
- `pause/revise/extendBudget/acceptLimitations` 的非运行态兼容编辑也携带版本；尤其 pause 的异步等待窗口不能覆盖另一个连接的新进展。
- 事件归属和释放已完成任务会话改用 `taskIdForSession` 索引查询，避免解析全库任务。启动先读取 header；实际执行前再完整校验 taskState。
- `taskItems` 支持按状态、是否必测、出现编号及位置分页。仅活动状态查询使用 partial index；混合和未知状态不被过滤丢失。它是局部读取 API，当前主调度器仍保留完整 Task 内存模型，UI 详情也保持兼容全读。不能说所有热路径、所有前沿都已经懒加载。

实际 public create/start/waitForIdle 回归核对每次增量提交后数据库与内存完整内容一致；第一次实际派发后不再调用全量 save/read。独立测试还覆盖真实点击后注入持久 unknown 并冷重启，以及两个连接在运行启动/非活动暂停的异步窗口发生冲突，确认不会覆盖新派发记录和预算。机制脚本中的部分场景直接调用 private step，不独立证明增量运行时已接入；公共生命周期测试与接续协议补充这部分证据。

[存储契约、迁移和微基准](task-store.md)。v1/v2→v3 升级在单事务内完整核验，损坏则回滚；旧二进制拒绝 v3。未升级任何现有任务库。兼容 store.save 的无版本接口仍保留给既有调用者，但上述生产运行时编辑均使用 CAS。

## 性能与存储取舍

每种输入/规模独立进程 3 轮；单次修改一个 plan、最后 round 和 header。完整输入和最终业务内容摘要相同。大 header 包含真实 obligations.entries 结构；5000 项约 1.19 MB。活动页是保留历史末尾的 10 个待测项，实际 SQL 查询计划验证命中活动索引。

| 工作负载 | 基线 → 本轮 |
| --- | ---: |
| 1000 项、小 header，单次保存中位数 | 2.336 → 0.111 ms（约减少 95%） |
| 5000 项、大 header，单次保存中位数 | 13.833 → 2.092 ms（约减少 85%） |
| 5000 项、大 header，读取 10 个活动项 | 17.518 → 0.297 ms |
| session 归属查询，单任务样本 | 2.86–16.86 → 0.015–0.017 ms |
| 完整任务读取 | 慢约 12.5%–17.1% |
| 关闭后的任务 DB | 增加约 15.4%–26.5% |

独立出现编号及索引有空间成本；partial index 降低了一部分开销，尚未抵消新增成本，WAL 口径也更大。全部负面结果和中途试验保留在专项证据中。

仍然存在的成本：header 内的 obligations/routes 每次整体序列化；当前 round 的栈、路径和审阅记录每次整体保存；启动全历史核验与调度进展摘要仍扫描历史；追加成员需要复制冻结数组；UI 详情没有分页化。因此本轮只证明避免反复序列化未变化的 plan/历史 round，以及特定查询加速，不是整个调度 O(delta)，也不是浏览器端到端延迟改善。

## 验收和后续边界

原四协议双方各 80 次：条件 25、接续 15、输入 10、恢复 30。双方均使用相同目标恢复 API；四协议脚本 SHA 一致，源码前后未变。原始结果在 `evidence/baseline/` 与 `evidence/after/`。

| 验收项 | 基线 → 本轮 |
| --- | --- |
| 共享标识的 A/B 都实际执行 | 0/5 → 5/5 |
| 条件协议声明分支的实际覆盖 | 35/40 → 40/40 |
| 非局部 A/B 都实际执行 | 5/5 → 5/5 |
| 恢复正例：实际到达且继续 SDK 输入 | 20/20 → 20/20 |
| 不可达/unknown 安全拒绝，虚假到达 | 10/10 → 10/10；均 0 |
| 输入目标对应正确，实际输入 | 40/40 → 40/40；均 30 次 |
| 每组 100 次报价更新的计划/待测增长 | 均 0 |
| 冷重启 unknown 保留并阻断 | 5/5 → 5/5 |
| 必要重入，无理由重入，重复叶动作 | 均 15、0、0 |
| 待测范围遗失，错误结清 | 均 0、0 |
| 接续协议 JEV / LLM 总调用 | 均 45 / 0 |

35/40 与 40/40 是各轮分支机会的合计，包含 5 次重复实验，不表示 40 个全局不同的 UI 分支；新增收益是每轮补上 shared:A。恢复正例要求实际页面到达后能够继续 SDK 输入；拒绝例单列。unknown 后尚未执行的 B 必须保留待测，不能计作成功。该协议 unknown 重启后新会话、动作、恢复和模型调用均为 0，没有测量 observe 调用；新增 public 运行时冷重启测试另外验证 observe 也未调用。后测与工程回归并行，不用这些墙钟时间宣称恢复更快。

以下任一证据会推翻本轮接受结论：同名 A/B 错误共享覆盖；语义无法区分时仍执行；unknown 经重启变为成功或允许新派发；某次已提交任务与运行时内存不同；版本冲突后旧任务覆盖新预算/unknown；故障留下半份任务；性能收益来自跳过必要身份/恢复核验。

尚缺真实 OKX 同预算多轮对照、长期任务库增长与证据清理数据、无可区分语义控件的可行探索策略。下一步如以压缩为目标，应单独测量 header 投影/历史记录分离、二进制摘要与更紧凑索引；不能简单删掉 unknown 或未测记录来缩小数据库。本轮未实现这些后续方案。
