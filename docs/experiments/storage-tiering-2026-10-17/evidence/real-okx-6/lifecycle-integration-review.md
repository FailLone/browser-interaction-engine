# Independent lifecycle integration review

This review follows the working-tree completion/availability/v3 integration after baseline `f6d7b9e`. It is not a frozen-source approval. Product files were read only by this reviewer; the two dedicated regression test files and this report are the only new review work. The initial completion/discovery review used no browser, provider, service or original/frozen database constructor. A later parent-authorized SDK regression phase used one local loopback browser fixture per invocation, then independent in-memory snapshots; it never accessed real sites, providers, or original/frozen databases. Tests stopped at each root-announced joint-test source freeze.

## Findings and disposition

1. **Direct completion could discard older sources. Fixed and independently tested.** The new completion gate reads discovery references and attempt-ledger references, rejects missing/foreign/unknown/executing attempts, and requires an exact source/action receipt or matching SDK correspondence for every retained source member. Coverage reconciliation now reads `item.attempts[].evidence` too. The independent ten-case test passes, including the later reconciliation path. The complete baseline archive preserves five failures out of the original eight cases.

2. **A newly audited source could be absorbed by a closed successful row. Fixed and independently tested.** `gap` originally found a succeeded exact-key item before applying the unfinished-only availability helper. A region-blocked B source therefore joined old successful A while remaining hidden behind A's success. The current lookup prefers unfinished rows and excludes directly completed concrete rows; `recordOutcome` also excludes already succeeded derived rows from new-attempt append. Four independent tests passed through actual `gap`, `auditRemainingScopes`, and `recordOutcome`, preserving the complete old row and its execution receipt.

3. **A spent scheduling key suppressed source retention before audit. Fixed and independently tested.** The original fifth discovery test put A's v3 key in `round.tried`, kept A successfully closed, and supplied B with an equal scheduling hint but SDK correspondence=false. Audit omitted B's source; that expected failure is retained in `discovery-five-tried-red.log`. Audit now records all unproved current sources independently of retry eligibility. Its separate `exactSourceExecution` reads the SDK ledger once per synchronous audit and only recognizes an actual succeeded, after-observed receipt with matching session/before/action ID/local ID/kind/value and a retained task reference. Fake task success, unknown/executing SDK receipts, foreign coordinates and missing after-observation do not qualify. A partial A+B aggregate may retain B's exact receipt without marking A complete. The expanded twenty-case test passes. The old successful row, unresolved A source and spent retry key remain intact.

4. **Explicitly selected old condition children require encoding compatibility. Closed by the normalization owner.** A pre-upgrade v2 split child selected via `revise(..., supplement=true)` becomes `dispatchScope=true`; it must retain its bound condition. The latest normalizer accepts such `conditionLineage.kind==='condition'` children, preserving original policy/key, split allocation and authority while supplying a v3 scheduling hint. The owner's selected/unselected child regressions are present. Its latest compact representation retains reference triples and distinct legacy keys, with an integrity checksum and exact-reference/schema validation; it is a scheduling hint, not SDK correspondence.

5. **Cross-reason availability aggregation could lose an alternate prerequisite entrance. Fixed and independently tested.** Existing evidence references can lead `scheduledRecovery` to a saved checkpoint, and recorded routes/DFS hints may also recover a source, so source aggregation does not inherently lose every route. However, local `entryTargets` first filters via `entryObligations` against `item.prerequisites`, before route reconstruction. If old `observed_in_scope` work used entry A and a newly blocked source used entry B with no saved checkpoint/route, keeping only A's path and writing B's path to an unconsumed audit event made B ineligible. The new cross-reason helper now requires complete prerequisite-path equality. Actual `gap`/`entryTargets` tests show different paths remain separate selectable unfinished rows, equal paths still aggregate both source references, and unrelated unknown work remains unchanged. This change does not expand or replace the preexisting same-reason exact lookup contract.

## Static boundary checks

- **Sources and unknown:** direct completion validates source ownership and exact observation/action coordinates. Missing material fails closed. Unknown/executing attempts in either retained ledger prevent completion; current B success cannot overwrite them. Exact receipts do not require a same-shaped after-page. The ordinary successful literal user request keeps its separate one-shot meaning.
- **Availability is unfinished work:** the allowlist contains mechanical availability reasons; classification/risk, unknown result, capability, sampling, exclusion and recovery obligations remain outside it. The helper rejects attempted/resolved/migrated/split-lineage work and does not delete historical duplicates. Every accepted source remains in `evidence[]`; reason changes are audited with coverage/execution flags false. Complete prerequisite-path equality is now required for the new cross-reason aggregation. The event records the reason update and remains neither executable path proof nor an independent retry grant.
- **Normalization hash:** the checksum binds original policy/key, full task scope, source references, source action IDs, per-source v2 encodings and the v3 target hint. Initial construction reconstructs each source from stored observations and uniquely matching actions, validates attempt-before ownership, and requires all sources to share one v3 encoding. Subsequent append validation retains all previous references and checks the new ones. Removing/changing scope or references invalidates the cache. This is integrity of a scheduling projection over immutable retained facts, not a signed authority proof or SDK equivalence. Unknown underlying attempts are still checked by the SDK's recovery/completion paths.
- **Unverified source conditions remain unverified:** v3 changes only the recognized structural-item owner-token representation; branch projection still uses the v2 rules and unresolved marker. Record/template/slot/local key, target semantic binding, context and operation remain relevant. Opaque owners with no distinguishing captured semantic binding may share a hint; the source-audit finding above is therefore material. A same hint must not suppress recording or complete an unproved source.
- **Prior tried aliases:** `wasTried` checks current v3, same-frame v2, and validated retained v2 aliases, including the existing boundary-visit wrapper. It neither clears nor rewrites `round.tried`. Changed semantic binding does not consume an unrelated alias. The repaired error was reuse of this retry check as an audit filter; its dispatch-budget purpose is unchanged.
- **Recovery debt:** `recoveryRouteKey`, source target conditions, route condition versions and retry ledger keys remain independent of the new scheduling encoding. The original `operationConditionKey`, prior routes, attempted conditions and unknown records are retained. Read-only projection can expose a normalized current candidate, but strict recovery still requires the original SDK target/route checks. Source-return keeps its separate native-position contract and does not release strict debt.

No additional static permission or completion regression was identified in these reviewed paths. The twenty-case discovery suite and ten-case completion suite are reviewer-owned frozen tests; final joint validation is owned by the root task. The subsequent historical review-bound SDK correspondence change is independently checked below; final broad regression and real continuation remain parent-owned.

## Historical review-bound operation correspondence

The stricter all-source gate exposed three existing semantic fixtures in which the operation was initially retained with unknown risk, then explicitly reviewed and successfully executed. The old direct-success shortcut had hidden these earlier unproved sources. The narrow SDK clarification now runs only for an actual successful retained attempt in `operationCorrespondence(s)`, after the original identity/unique-target checks, when the normal operation samples are missing or differ. Browser composition validates the single `reviewed-control/v1` proof against its stored record, reviewer and source-observation coordinates, the record's own condition checksum, and exact source-before/old-target `controlReviewConditions`.

The target, successful source-before, and retained original review observation must preserve the exact review binding and captured `reviewAttributes` (including data/name attributes). The original review observation is reloaded and validated; missing, foreign, incomplete, changed-rule or later-than-review source material rejects projection. These observations retain the same unique instance in the same session/document, with equal nonempty rule versions and complete known context. Captured times must be finite and ordered old target <= source before <= attempt start; the review must predate the attempt. Revoked/superseded/unknown-status records and revoked or cyclic reuse parents fail closed. An invalidated review is accepted only when its invalidation names this successful attempt's exact after-observation. This coordinate matters: `reviewActions` can invalidate a review during the after capture, before the engine writes `finishedAt`, so a later-than-finished timestamp rule would incorrectly reject an ordinary successful transition. An unrelated later observation or an earlier invalidation is not accepted.

The temporary projection changes only unknown/interface risk and unsupported basis to the verified review-backed sample. It preserves target coordinates, operation kind/value, raw observations, action rows and preconditions. Both samples still use the original adapter `controlCase` and full `browserBranchConditions`; hidden, nonlocal, changed or unresolved selector evidence therefore continues to reject equivalence. It does not make a new DOM instance correspond, cover a different A/B binding, clear unknown outcomes, grant replay, restore a checkpoint, or authorize execution. Target-arrival and repetition APIs do not use this projection.

`tests/reviewed-operation-correspondence.test.ts` has 51 cases built from one genuine local SDK review/execution per test-file invocation. After capturing the seed, the local page/browser closes and each counterexample constructs a separate `MemoryStore` with a non-attached `BrowserEngine`. Checks include the successful old-source correspondence, no writes/events/identity changes, tentative basis, exact-after invalidation, failed/unknown/executing/missing receipts, changed instances and duplicate instances, changed parent/handler/rule/context and data-record binding, original-review source integrity, different input, hidden nonlocal change/unavailable evidence, foreign/missing/corrupt/forged review proof, revocation/supersession/reuse revocation/cycle, invalid timing, and negative target/repetition contracts.
