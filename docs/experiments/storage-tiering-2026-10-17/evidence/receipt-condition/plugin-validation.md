# Plugin receipt-condition checkpoint

Conclusion: a real successful command is retained as execution history, but it cannot complete its own retained source condition without the SDK's public receipt-condition proof. Missing evidence leaves that obligation unresolved. This change does not grant arrival, replay, identity, or additional retry budget.

Base revision: `3cd2ac5c1f59b840950270af8434f38632813c47`. Validation used uncommitted product changes. `plugin-validation.json` records the exact source hashes, commands, exit codes, and original log hashes. `validatedSourceSha256` describes the 57-case run; `followupValidatedSourceSha256` describes the later two-case review checkpoint. Earlier logs came from intermediate source and have not been relabeled as either build. Parent-owned SDK changes were present; their separate validation is recorded in this directory. Each snapshot was frozen when its corresponding logs were archived.

The red case uses an independent local server, headless browser, MemoryStore and temporary plugin store. The checkbox's actual handler reads owner B, the actual receipt is succeeded, and the unchanged retained before observation still says A. Before the fix, real `recordOutcome` marked A succeeded. After the fix, the same actual receipt and consumed attempt remain while A stays unresolved. The final suite also exercises the real stable same-document positive case. All owned browser/server resources were closed; no original task database, browser, provider, or real OKX service was used.

The initial related failure was a missing `boundaryState` method in the new final-round protocol fixture, not a failed product assertion. That fixture was repaired. Final checks additionally cover excluded/nonrequired projection order, unknown precedence, and prevention of a scheduling alias hiding an old completion with missing receipts. The original completion-evidence (7), condition-migration (11), and scheduling-key-runtime (3) checks passed in the related run and were not repeated. The three existing isolated source/discovery/factory fixtures now explicitly supply the public receipt-condition response; their positive stubs do not fabricate real DOM witnesses.

Protocol fixtures cover portable/document response consumption, actual supplied-value hash ownership, unavailable capability, per-call memo behavior, and a persisted temporary task reopened in a new plugin instance. Old completed tasks with missing evidence become blocked without creating a browser session; original source references, actual attempts, tried keys and route debt stay intact. The old exhaustive declaration and resolved obligation projection are withdrawn. A missing-condition item waits without suppressing independent newly observed work. Explicit supplement releases waiting only, keeps the old diagnosis and sources, and does not itself prove completion. Sufficient SDK proof for every retained source can still settle a waiting item.

The final-round revocation case is explicitly a public-protocol stub: it verifies that the last completion audit rechecks receipt conditions and preserves uncertainty. It is not a new real-browser review-revocation experiment, and does not establish that every legacy coverage display now follows the new query. Existing cross-source correspondence remains on its original SDK interface and hot path.

No performance benchmark, full suite, or 80-trial protocol was run for this plugin patch. One synchronous completion/audit memo avoids duplicate queries for the same session and receipt; different receipts can still each scan SDK session ledgers, so M receipts over N records can cost O(M×N). This is a correctness checkpoint, not a speed claim. Parent owns final root/core type checking and independent review.

Follow-up review found that a legitimate later peer proof must take precedence even when the old item still retains its own `resolvedBy`. Reconciliation now includes every referenced peer and its actual attempt references without deleting old history. The expanded checkpoint verifies that the settled item stays succeeded on another audit, while a missing or unknown peer rejects completion and the original sources/tried keys remain unchanged. Its first run exposed an optional-audit comparison calling `digest(undefined)` for a legacy succeeded peer; comparing an absent audit as null fixes that local failure. A separate checkpoint confirms that a nonrequired old success may receive an unverified diagnostic without reopening its required parent, withdrawing the selected-scope exhaustive claim, or starting a new session. The action fixture also now supplies the required `source` and `sampleValidity` fields; parent owns the final typecheck. Only these two affected cases were rerun; the 57-case log retains its original snapshot.
