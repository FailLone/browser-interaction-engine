## 实际调用链与边界

`reachExplorationTarget / reachCheckpoint → reachInternal → NavigationIndex.refresh → RecordedNavigationGraph.path → replay → runAction → 当前事实验证`。

1. `NavigationIndex` 初次读取 retained attempts/transitions，仅解码成功且可重放操作所引用的观察。之后使用可选 `Persistence.entityChanges` 读取变化的 ID，更新受影响边；被动观察不会自动成为路径边。观察、操作正文不留在缓存，只保留严格状态摘要、依赖索引和成本汇总。公开 `navigationPath` 仍返回最少步数的提示路径；实际恢复使用成本排序。
2. Memory/SQLite 实现 4096 条有界进程内变更环。历史修改、回滚、游标过期、SQLite 外部连接或直接数据库写入使索引重新读取；读前/读后核对游标，连续两次并发变化则明确失败。SQLite 事务内允许一次性全量查询，数据与游标不能复用到下一次查询。第三方存储未实现接口时维持每次全读兼容行为。没有新数据库表或持久变更日志。
3. 每次真实 replay 把 `recoverySegment` 写入对应的实际 `ActionAttempt`：历史来源、条件 key、耗时、target/checkpoint 模式，以及 matched/no_progress/diverged/unknown/unverified。它们是路线评价证据，不修改行动结果，也不是到达或覆盖证明。
4. 评分按规则版本、已声明上下文、操作及输入、目标身份与绑定、适配器来源条件区分；条件不可判定时回退严格观察 key。已知条件不因无关价格文字改变而生成新的失败 key，但**图端点仍严格匹配，未放宽状态等价或发明跨价格状态的连边**。A 的失败不能凭控件名称转给 B。
5. 未测路线统一先验成本 1000，保留原最少步数及稳定同成本顺序。已测路线取分段耗时均值，按 250 ms 向上取整，加 `4000 × 已知失败占比` 的有限惩罚；计分耗时限制在 1–60000 ms，原始耗时完整保留。该值是可审计的排序启发式，不是经过校准的恢复时间/成功概率预测。未知与无法归因的目标偏差不训练成功或失败；target 模式的被动变化保留 unverified，不把最终目标未到达全部归咎于最后一步。
6. Dijkstra 只选择路径。当前唯一对应、输入、来源条件、重放权限、预算、执行约束仍逐步验证；unknown 立即阻断替代路线，不能借另一路线或新会话改记成功。每次恢复仍最多四个计划，已成功的嵌套前缀不因后续失败重放。
7. 若加权路径超过当前剩余动作数，用相同首步许可谓词查询最少步路径；存在能容纳的路径时优先使用，并在选择事件记录 `remaining_action_budget`。每次重规划重新读取剩余额度；没有预算内路径时仍由原有逐步预算检查约束。该回退保障已知可达机会，不保证预算约束下成本全局最优，也未预测墙钟截止时间。

缓存可被丢弃，重启后从执行记录重新构建成本。四会话 LRU 只限制会话数量，**索引总内存仍与保留历史量相关**，并非固定字节预算。正在恢复时其他查询可能刷新共享索引；已选路径仅是提示，执行检查不缓存。

## 可复现的收益

- 同源码的五路线用例：前四条当前失效，第五条可用。旧版本第一、二轮都重复 `[0,1,2,3]` 并返回 UNREACHABLE；新版本第一轮同样停止于四个计划，第二轮选择 `[4]`，TARGET_REACHED 后通过 SDK 输入 `45`，页面 input 事件证实发生。没有扩大单轮预算或删除待测目标。证据见 `evidence/recovery-route-cost-fifth-comparison.json` 及两份日志。
- 简单路线重复恢复由两次实际点击 `[0,1]` 降为一次 `[1]`；嵌套场景由 `Open,0,1` 降为 `Open,1`。target/checkpoint 均验证；条件 A→B→A、当前权限撤回和最低成本路线出现 unknown 均有反例测试。
- 仅耗时、无失败惩罚的索引测试中，已测两步路线可优于较慢的一步路线；冷构建仍作相同选择。该项使用注入计时事实，不冒充浏览器延迟对照。
- 独立浏览器复核发现加权路线超出剩余操作次数的回归：剩 1 次操作、一步直达较慢、两步路线较快时，早期 `0d01be1` 点击 Open 后耗尽预算；只允许直达的对照能成功。已保留 `evidence/budget-before` 的实际页面证据，只有已测分段耗时被注入，没有伪造状态或执行许可。最终 `7ec9665` 增加上述回退：target/checkpoint 两例在剩 1 次时均一步直达，剩 2 次时仍选便宜的两步路线。相同测试在旧实现均失败、应用补丁后 2/2 通过，临时归档日志和补丁哈希见 `evidence/budget-regression`。最终修正与验收单独列出，不能用修正前的全套结果覆盖这项回归。

### 路径查询成本

同一公共 API 基准脚本、独立进程顺序执行，合成 1000 条历史边与 1000 次被动观察；预热后各 7 组、每组 20 次查询。每次路径完全一致，撤销权限立即返回无路径，再恢复权限后完整路径一致。详见 `evidence/benchmark-comparison.json`。

| 指标 | f46a750 基线 | ebdb65f 图算法实现 |
| --- | ---: | ---: |
| 稳态每次查询中位数 | 12.226 ms | 0.228 ms |
| 首次构建并查询（各仅 1 次） | 14.007 ms | 32.517 ms |
| 140 次稳态历史观察读取 | 140420 | 0 |
| 140 次稳态 attempts / transitions 全读 | 各 140 次 | 0 |

稳态减少约 98.1%，但冷构建本次变慢约 2.32 倍；首次构建样本不足，不能称为冷启动分布。基准只覆盖内存存储与公共路径查询，**不能写成浏览器恢复快了 53.7 倍**，也不能推断任务全量读取变快、内存或磁盘减少。最终包装层修正没有更改这段算法；另用实际 BrowserEngine 验证包装后重复查询不再全读、撤权后立即失去路径。

独立审阅确实发现过 BrowserEngine 的 RetainedPersistence 未转发新接口，导致早期实现只有排序收益、没有 SDK 索引收益。已补转发及无此接口的兼容测试；在 `ebdb65f` 启动的两项广泛验收提前结束，部分记录放在 `evidence/interrupted-ebdb`，不作为最终通过证据。

## 尚缺与推翻条件

受控反例支持“条件化排序比每次遗忘失败更有效”，不能据此推断真实 OKX 的总体恢复成功率、P95 耗时或穷尽程度。尚缺真实站点同预算、多轮、动态内容及长期历史规模的对照。新分段字段及审计事件会增加少量执行记录体积，本轮不声称任务库变小；冷索引构建仍需要全量历史扫描。

频繁被动变化还可能使已到达的分段无法严格归类为 matched/no_progress；target 模式此时保留 unverified、不累计正负经验。因此动态页面可能学习较少，不能只看条件 key 稳定就声称所有恢复失败都会被优化。

若出现缓存权限撤回不生效、跨 A/B 错用失败经验而漏测、unknown 被清除、实际未到达却报告成功，必须先修复，不能接受为性能权衡。若受控与真实多轮中错误路径开销、新覆盖产出和恢复成功率无改善，或计分/缓存成本超过节省，应重新评估评分与缓存适用范围，而不是继续扩大状态归并。
