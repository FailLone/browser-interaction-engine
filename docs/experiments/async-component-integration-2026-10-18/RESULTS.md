## 修复与反例

原 OKX 脚本替换了 `BrowserAdapter.prototype.execute/readDOM`，触发了 SDK 的默认实现身份保护，从而不给派发凭证。新入口在原生实现内部发送同步、分离的数据记录，读取结束回调在原生输入结束后交付。它不给观察者 Page、DOM 原始返回值或凭证写入能力。自定义 execute/readDOM，即使调用原实现，仍无法取得该凭证；伪造 DOM 的反例也仍被拒绝。恢复启动和拒绝派发均有计数测试。

补入旧目标仍 enabled 的真实插件场景后，第一次测试实际失败：旧目标执行两次，迟到子链接未执行。原因是新子项等待区域登记，而旧目标在新条件下提前让调度退出登记步骤。现在先完成就绪、已授权导航的确定性区域登记，再交给原调度器选择。新子项有独立回执；旧目标改变条件后产生的义务仍 unresolved，没有把不同模式合并。

原历史 OKX 的独立诊断吻合此机制：12:06:48.290 子项已 ready；50.914 有 43 个候选被 region review 阻塞；51.339 只有现货入口可执行，另有原 loading-region hover 待办；51.489 仍选入口并于52.425派发；区域登记直到57.423才发生。USDT、Crypto 的就绪候选明确被 `region_review_required` 阻塞；几个币对链接还需原 list decision。真实 Crypto 模式和目的地差异全部保留。

永久 pending 测试另发现一个截止时间边缘：循环等待后只剩很短时间却再次读取，超时清掉了之前有效的独立证据。现在下一次内容采样必须同时容纳采样间隔与有界读取余量，仍沿用原 deadline；未知内容不被解释为完成。

## 剩余失败边界

1. 帮助页上的现货入口、USDT和Crypto已取得真实原生凭证且条件核验通过，证明计量包装问题得到修复。
2. 首次ETH/BTC导航有真实派发凭证，目标依赖范围完整；但它跨 document，而当前 document coverage reader 明确要求 before/after同 document。该策略不能为这个不具备portable sample的导航回执提供条件证明，原待办因此保留。
3. 交易页仍出现`dispatch_witness_missing`。其目标局部根完整，但全局owner graph已到768节点，页面其他选择器存在node_budget/target_not_captured；当前派发凭证还要求整个graph hash相等。最终派发前DOM样本未完整保留，不能把实际每一次缺失精确断言为某一字段。
4. 独立原生驱动反例验证了全局依赖问题：同一导航More，外部数值输入保持1时回执可核验；只在派发前把外部输入改为2，More实际仍打开，但凭证和条件证明撤回。两例分别28/30条完整本地调用、567/481ms，各2条启动/派发，不用模型。这是机制反例，不冒充真实OKX最终DOM样本重建。

因此本轮没有放宽graph相等、删除不完整依赖、伪造跨document收据或用LLM绕过条件核验，也没有重复相同失败轨迹。余下需要独立、可检验的导航回执和局部依赖证明设计；组件相似度不能代替它们。
