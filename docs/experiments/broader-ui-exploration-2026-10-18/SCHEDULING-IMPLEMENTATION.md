# 源码诊断后的调度实现

这是 SCHEDULING-DIAGNOSIS.md 后的实现记录，不替代原验收协议，也不把历史失败改为通过。

程序探索通过 `selectProgramWork` 统一选择下一项工作。当前动作仍先经过原有作用域、操作授权、可见性、依赖、唯一性与 SDK 可执行检查。选择器只排序，不授权。

1. 真正的 modal/dialog 保持内部工作优先；内层退出后重新观察父层，未授权或未知义务继续保留。
2. 已选择的恢复目标或原入口续接保持优先。返回源页后的新文档实例不能让背景动作抢走已选择的原路径；入口仍须通过必要重放证据。
3. 当前未采样候选可继续，包含真实新目的地。程序模式不再使用四次动作额度或新 URL 重置额度来决定切换。现有非程序模式调度不变。
4. 当前候选耗尽，或仅有已采样操作/已访问位置时，评估原有保留路径。候选返回路径仍须经 SDK 实际到达验证；返回页不等于恢复了原控件。
5. 没有可行返回路径时，可继续已经入选但优先级较低的当前工作。原条件、义务、失败和未知都不删除。

跨文档的捕获 targetBinding 可以保留采样排序提示。同源页面 URL 不再给相同绑定重新赋予“从未采样”优先级；不同来源仍分开。没有捕获绑定时继续使用完整原 scope。这个提示不用于身份合并、回执、覆盖、授权或重复执行许可。已观察目的地集合只影响遍历排序；它不认定两个 DOM 状态相同。

同一已展开分支内，已具备原生依据的工作排在用途未知的 hover/focus 观察之前。重新选择旧分支时同样优先具体操作；未知观察继续保留。页位置恢复先于尚未解决的控件解释恢复，避免后者在动态页面上先做全局刷新而失去可用的原生位置。每个候选仍走原有路径检查，实际结果不由排序规则保证。

## 动态页面上的返回位置

`navigationPositionCapture` 来自一次当前 capture 内的至少两次 URL/document 样本以及匹配的浏览器 GET 历史项。它可以证明本次位置已独立稳定，即使无关报价字段持续变化。这个证据不继承旧导航动作的效果，不证明旧控件已返回，不代替 sourceReturnCondition、历史项可返回性、上下文、边界或实际到达验证。

执行后自行禁用的目标可以完成本次局部依赖观察；它不会因此变为 enabled，也不能再次通过 dispatch 的 enabled 检查。
