# Program-first exploration: implementation boundaries

The product executes caller-authorized, mechanically ready public navigation and bounded observations before optional semantic review. Unknown duties remain in the coverage ledger. A successful hover or recovered page does not complete a retained click obligation.

## Position, operation reference, identity and completion

| Evidence | What it establishes | What it does not establish |
| --- | --- | --- |
| Native document/history position, observed GET method bound to CDP loader | A new document was reached; two complete samples can establish document readiness even while a quote/input changes | Stable destination controls, original-child arrival, business-state equivalence |
| Original reveal observation and recorded entry path | Where an immutable pending child was discovered and which actual entry can restore it | Permission to execute a stale control or completion merely from reopening a menu |
| Complete native-navigation operation reference v2 | Unique current correspondence for the captured native operation, with complete local navigation-owner structure, destination, IDREFs, handlers and context | Logical control identity, replay permission or whole-page equivalence |
| Current SDK dispatch validation and durable receipt | Actual execution of the separately validated action under its recorded conditions | Arbitrary JavaScript dependency independence, business correctness or site exhaustion |

Native reference v2 ignores class/style presentation and ancestry outside the nearest captured navigation landmark only in this operation projection. Raw observations, logical identity and global classification bindings are unchanged. Current visibility, obstruction, readiness and permission are rechecked at dispatch. Changed destination/business attributes/ARIA/context, missing or rival structure and ambiguity continue to reject.

The real rebuilt-list fixture has no fixed anchor IDs. It reconstructs `li/a` instances across navigation, changes hover styling, includes multiple source observations and unrelated pending identity hypotheses, and uses a changing destination. Old and new instance IDs and stable keys differ. The original item still requires the original reveal/path source, a new entry execution, independent arrival and its own later durable child receipt. This counterexample is in `tests/program-navigation.test.ts`.

Original children are retained immediately after the successful reveal, before preparation recaptures. Pre-dispatch source associations are persisted with the exact pending request/action/frame. Completion independently verifies every retained source after execution; a crash does not replace the original item. Historical correspondence queries are permitted only for the exact already-executed action with a durable condition-verified receipt. This is a read-only audit path, never a fresh execution or identity grant. Unexecuted stale targets remain rejected.

## Optional models

The current extension handles concrete classification and operation-effect ambiguity. A visible, ready current target must have its own captured operation evidence and be inside caller scope and the active boundary. Independent program actions and verified recovery have priority. Program capture, actual attempts and transition outcomes, SDK blockers and probe availability are saved first; a permitted bounded probe is tried once or its earlier receipt is retained.

Each gap supplies one explicit question to the existing review/router, with at most two actual provider calls and a 12-second cancellation deadline inside the task budget. The durable negative key excludes capture IDs, position and presentation. It never grants identity, permission or coverage. Unchanged closed evidence is not re-asked after recapture or serialized task restoration; an interrupted provider call cannot reset the allowance. Pure structural unknowns and requests for smarter ranking do not trigger calls. No new region or orchestration model was introduced.

Model answers return through the existing SDK review validators. Traces distinguish the question, actual calls and time, accepted/rejected SDK review, newly executable operations and subsequent actual condition-verified receipts. Offline, uncertain and timed-out calls retain the unknown duties. Diagnostic gain measurement cannot turn an accepted SDK review into a rejection. A later receipt is operation evidence, not business correctness. General model repair of identity or arbitrary recovery is not implemented.

Controlled-provider real-browser tests show a useful operation review enabling one actual later click, and zero such gain for uncertainty, offline or timeout. They also verify ready work first, actual bounded hover first, same-evidence deduplication and the independent gap deadline. These are fixtures; the real-provider OKX comparison is reported separately.
